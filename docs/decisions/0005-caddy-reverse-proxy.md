# ADR 0005: Caddy as the reverse proxy

- Status: **Proposed** (owner chose Caddy 2026-11-16; domain model open: D4)
- Date: 2026-11-16

## Decision

- One Caddy container per server publishes ports 80 and 443 and routes each school's domain to its app container.
- Routes come from a **Caddyfile generated by Ansible** from `schools/<server>.yml`. This keeps routing reviewable in Git.
- Alternative considered: `caddy-docker-proxy` (routes from container labels). Attractive, but adds the Docker socket to the proxy container and its last commit is over a year old. Revisit if Ansible-generated routes become painful.

## Certificates

| Domain model | Approach |
|---|---|
| Subdomains of one product domain | Per-host certificates (simple), or a wildcard certificate via DNS challenge (needs a Caddy build with the DNS provider plugin) |
| Each school's own domain | Caddy on-demand TLS with an `ask` endpoint that approves only domains listed in `schools/` |

## Django settings per school

- `DJANGO_ALLOWED_HOSTS` = the school's domain.
- `DJANGO_TRUSTED_PROXIES` = the Docker network range of Caddy, so the existing `SECURE_PROXY_SSL_HEADER` logic and source-address hashing work.
- HTTPS stays on (the app refuses to start with `DJANGO_HTTPS=False` outside debug).

## Consequences

- Security headers stay in Django; Caddy adds compression and access logs with rotation.
- A hostname alone is not a security boundary; isolation comes from separate containers, `.env` files and database logins.
